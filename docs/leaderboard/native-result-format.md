# Native Evaluation Result Format

Community submissions preserve the output generated by the PolyCodeEval
evaluators. Participants do not convert per-task records to another schema and do
not rewrite `summary.json`.

## Directory layout

```text
evaluation/
  summary.json
  cpp/
    <project>/
      <task>.json
  go/
    <project>/
      <task>.json
  java/
    <project>/
      <task>.json
  javascript/
    <project>/
      <task>.json
  python/
    <project>/
      <task>.json
```

Only languages represented by submitted tasks need to appear. A task identity is
stored in the JSON as:

```text
<language>/<project>/<task-name>
```

The corresponding path is:

```text
evaluation/<language>/<project>/<task-name>.json
```

Task names, case, and punctuation must remain unchanged.

## L0/L1 per-task records

L0 and L1 use the same project-level result family. A native record can contain
the following fields:

| Field | Type | Meaning | Metric use |
|---|---|---|---|
| `task` | string | Canonical task identity | Required identity |
| `solver` | string | Evaluator solver label | Audit |
| `passed` | boolean | All functional tests passed | Full-pass rate |
| `build_status` | string | `ok`, `compile_error`, or `runtime_error` | Build-success rate |
| `test_mode` | string | `blackbox` | Configuration check |
| `test_details.tests` | array | Parsed test names and boolean outcomes | Audit |
| `test_details.passed` | integer | Parsed passing tests | Correctness |
| `test_details.failed` | integer | Parsed failing tests | Correctness |
| `test_details.total` | integer | Parsed test count | Correctness |
| `result_schema_version` | string | Native scoring-schema revision | Compatibility check |
| `score_scale` | string | Native dimension scale, currently `0-5` | Interpretation |
| `score_formula` | string | Native full-quality formula | Compatibility check |
| `radar_scores.Correctness` | number | Functional correctness on `[0, 5]` | Execution and quality |
| `radar_scores.Faithfulness` | number or null | Prompt faithfulness on `[0, 5]` | Full-quality only |
| `radar_scores.Architecture` | number or null | Repository architecture on `[0, 5]` | Full-quality only |
| `radar_scores.Health` | number or null | Static repository health on `[0, 5]` | Full-quality only |
| `overall_score` | number or null | Weighted quality score | Full-quality only |
| `dimension_details` | object | Evidence and status for each score dimension | Audit |
| `judge_reviews` | object | Preserved Faithfulness and Architecture reviews | Audit |
| `exit_code` | integer | Evaluation process exit status | Audit |
| `duration_seconds` | number | Task duration | Audit |
| `stdout` | string | Captured standard output | Audit; public in PR |
| `stderr` | string | Captured standard error | Audit; public in PR |
| `error` | string | Evaluator exception when present | Audit |
| `inferred_commands` | object | Commands selected by the evaluator | Audit |
| `attempts` | array | Recorded command attempts | Audit |
| `retries` | integer | Retry count | Audit |

`build_status = "ok"` means tests ran or the process exited successfully.
`compile_error` identifies recognized build or dependency failure output before
tests were parsed. Remaining pre-test failures use `runtime_error`.

In `correctness_only`, `radar_scores.Correctness` is populated and the other
three dimensions are null. The task's native `overall_score` may equal
Correctness; the result remains excluded from the full-quality ranking because
the other dimensions are absent.

In `full_quality`, all four radar values and `overall_score` must be present for
every submitted task. The current native formula is:

```text
0.4 * Correctness + 0.25 * Faithfulness
                    + 0.25 * Architecture + 0.1 * Health
```

## L0/L1 summary.json

The native project-level summary contains:

- `solver`, `total`, `passed`, and `pass_rate`;
- `scored_tasks` and `scoring_coverage`;
- `avg_overall_score`, `avg_correctness`, `avg_faithfulness`,
  `avg_architecture`, and `avg_health`;
- `by_language` and `by_project` aggregates;
- `test_case_stats` when parsed test details are available.

The summary describes task records present in the local output directory. Public
ranking metrics are independently recomputed against the complete release
denominator.

## L2/L3 per-task records

L2 and L3 share the same execution-result family:

| Field | Type | Meaning | Metric use |
|---|---|---|---|
| `task` | string | Canonical task identity | Required identity |
| `solver` | string | Evaluator solver label | Audit |
| `passed` | boolean | Underlying runner reports full success | Full-pass source |
| `compile_passed` | boolean | Build succeeded or parseable tests were observed | Build-success rate |
| `full_passed` | boolean | Native copy of the task-level full-success result | Full-pass rate |
| `test_pass_ratio` | number | Parsed passed tests divided by parsed total | Test score and diagnostics |
| `compile_score` | number | `0.5` for build success, otherwise `0` | Execution score |
| `test_score` | number | Half of test-pass ratio after build success | Execution score |
| `score` | number | Compile score plus test score | Execution score |
| `test_details.tests` | array | Parsed test names and boolean outcomes | Audit |
| `test_details.passed` | integer | Parsed passing tests | Consistency check |
| `test_details.failed` | integer | Parsed failing tests | Consistency check |
| `test_details.total` | integer | Parsed test count | Consistency check |
| `test_mode` | string | `both`, `whitebox`, or `blackbox` | Configuration check |
| `exit_code` | integer | Evaluation process exit status | Audit |
| `duration_seconds` | number | Task duration | Audit |
| `stdout` | string | Captured standard output | Audit; public in PR |
| `stderr` | string | Captured standard error | Audit; public in PR |
| `error` | string | Evaluator exception when present | Audit |

The current scoring relationships are:

```text
compile_score = 0.5 if compile_passed else 0.0
test_score    = 0.5 * test_pass_ratio if compile_passed else 0.0
score         = compile_score + test_score
full_passed   = passed
```

Scores and ratios are stored with native evaluator rounding. Validation allows
the corresponding rounding tolerance and reports material inconsistencies.

## L2/L3 summary.json

The native file- and function-level summary contains:

- `solver` and `total`;
- `compile_passed`, `compile_pass_rate`, and `compile_score`;
- `full_passed` and `full_pass_rate`;
- `test_score`, `total_score`, and `avg_score`;
- `by_language`, `by_project`, and `by_task` aggregates.

The native summary is checked against submitted task JSON files. Ranking uses an
independent aggregation with fixed release denominators.

## Missing tasks

Missing task JSON files are allowed. The public result reports the submitted and
expected counts. Every absent task contributes zero to fixed-denominator metrics.
The validator never creates synthetic files inside the submitted native result
directory.

## Files excluded from submissions

The native result directory contains evaluation evidence only. Exclude generated
repositories, completed L2 files, L3 function bodies, model response archives,
dependency trees, Docker layers, datasets, and build caches.
